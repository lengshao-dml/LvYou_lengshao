# 第 2 章 相关技术

## 2.1 Spring Boot 技术栈

本旅游城市推荐系统的后端服务采用 Spring Boot 框架构建，旨在提供高效、稳定的数据服务和业务逻辑处理能力。Spring Boot 凭借其“约定优于配置”的原则，极大地简化了 Spring 应用程序的初始化和开发过程。

**核心特性及应用：**
*   **快速启动：** Spring Boot 内嵌 Tomcat、Jetty 或 Undertow 等服务器，可直接打包成可执行 JAR 文件运行，无需部署到外部应用服务器，显著缩短了开发和部署周期。在开发环境中，启动时间通常控制在 5 秒以内。
*   **自动化配置：** Spring Boot 根据项目中引入的依赖，自动配置大量的 Spring Bean，例如数据库连接池、Web MVC 组件等，极大减少了手动配置的工作量。
*   **生产就绪特性：** 提供了 Actuator、外部化配置、内嵌监控等功能，便于系统的监控、管理和运维。通过 Spring Boot Actuator，可以实时获取应用程序的健康状况、度量指标等信息。
*   **Spring Data JPA：** 结合 Hibernate ORM 实现数据持久层操作。通过定义 Repository 接口，无需编写 SQL 语句即可完成复杂的数据库CRUD操作，支持复杂查询构建和分页功能，提升了开发效率和数据访问的便捷性。
*   **RESTful API：** Spring Boot 提供了强大的 Spring Web 模块，支持快速开发符合 RESTful 规范的 API 接口，实现前后端分离架构，为前端应用（如 Vue.js）提供标准化的数据交互接口，平均响应时间预计在 200ms 左右。

## 2.2 MariaDB 数据库

本系统采用 MariaDB 作为核心关系型数据库，用于存储用户的基本信息、偏好标签、城市特征数据、天气预报历史等结构化数据。MariaDB 作为 MySQL 的一个分支，提供了高度兼容的接口和更优异的性能表现。

**核心特性及应用：**
*   **高兼容性：** 与 MySQL 完全兼容，这意味着在开发和部署过程中可以无缝切换，同时享受 MariaDB 带来的额外优势。
*   **性能优化：** MariaDB 在查询优化器、存储引擎（如 XtraDB）方面进行了多项改进，尤其在大数据量、高并发的读写场景下表现出色。通过合理的索引设计，城市信息查询速度可提升 [30-50]%。
*   **高可用性与可扩展性：** 支持 Galera Cluster 等集群方案，可实现数据的高可用和读写分离，确保系统在面临高负载时仍能稳定运行，满足旅游推荐系统对数据一致性和可用性的要求。
*   **地理空间数据支持：** MariaDB 提供了对地理空间数据类型（GIS）的支持，这对于存储和查询城市经纬度、计算城市间距离等功能至关重要，为基于地理位置的推荐提供了原生支持。

## 2.3 Valkey (Redis 兼容) 缓存服务

为了提升系统响应速度和减轻数据库负载，本系统引入 Valkey 作为分布式缓存服务。Valkey 是 Redis 的一个高性能分支，完全兼容 Redis API，提供了丰富的数据结构和闪电般的读写速度。

**核心特性及应用：**
*   **极速读写性能：** Valkey 将数据存储在内存中，读写速度远超传统磁盘数据库。对于高频访问但更新不频繁的数据，如城市基础信息、天气预报结果、热门城市列表等，缓存命中率可达 [90]% 以上，将查询响应时间从数百毫秒降低至数毫秒。
*   **丰富的数据结构：** 支持 String、Hash、List、Set、Sorted Set 等多种数据结构，灵活应用于不同的缓存场景。例如，Hash 结构可用于存储城市特征信息，Sorted Set 可用于存储城市热度排行榜。
*   **数据持久化：** 支持 RDB 和 AOF 两种持久化方式，确保即使服务器重启，缓存数据也能恢复，增强了系统的可靠性。
*   **分布式与集群：** 支持主从复制和集群模式，可构建高可用、可扩展的缓存服务，应对高并发请求，预计单实例每秒可处理 [数万] 次请求。

## 2.4 Vue 3 前端框架

本旅游城市推荐系统的前端界面采用 Vue 3 框架开发，旨在提供现代化、响应式且用户体验友好的交互界面。Vue 3 作为一款渐进式 JavaScript 框架，具备高性能、易上手和灵活的特点。

**核心特性及应用：**
*   **组合式 API：** 提供了更灵活的代码组织方式，使得复杂组件的逻辑复用和维护变得更加容易，尤其适用于大型单页应用（SPA）的开发。
*   **性能优化：** Vue 3 在渲染性能、打包体积等方面进行了显著优化。例如，通过 Proxy 实现响应式系统，提升了数据响应的效率；编译时优化减少了运行时开销。
*   **响应式设计：** 结合 Bootstrap 5 等 CSS 框架，实现自适应布局，确保系统在不同设备（PC、平板、手机）上都能提供一致且优质的用户体验。
*   **组件化开发：** 将用户界面划分为独立的、可复用的组件，如“推荐卡片”、“筛选表单”、“城市详情卡”等，提升了开发效率和代码的可维护性。
*   **Pinia 状态管理：** 采用 Pinia 作为状态管理库，它是一个轻量级、类型安全的 Vue 状态管理库，提供了直观的 API，便于管理用户偏好、推荐结果等全局状态。

## 2.5 推荐算法理论

旅游城市推荐系统的核心是其推荐算法。本系统将根据用户多维度偏好和动态信息，融合多种推荐策略以提升推荐质量。

**主要算法思路：**
*   **内容推荐（Content-Based Recommendation）：** 根据用户的历史兴趣标签（如自然风光、历史文化、美食文化）和城市特征标签进行匹配。系统会分析用户明确选择或通过行为隐式表达的兴趣，寻找具有相似特征的城市进行推荐。例如，若用户喜欢“历史文化”类城市，则推荐文化遗迹丰富的城市。
*   **协同过滤（Collaborative Filtering）**：
    *   **基于用户的协同过滤：** 寻找与当前用户有相似偏好的其他用户，并将这些相似用户喜欢但当前用户尚未体验过的城市推荐给当前用户。
    *   **基于项目的协同过滤：** 分析城市之间的相似性，向用户推荐与其喜欢城市相似的其他城市。
*   **混合推荐（Hybrid Recommendation）：** 为了克服单一推荐算法的局限性，本系统将采用混合推荐策略。例如，可以结合内容推荐和协同过滤的结果，或者将基于用户偏好匹配的初步推荐结果与实时动态因子（天气舒适度、城市热度、地理距离）进行加权融合，生成最终的城市综合评分，从而提供更加个性化和上下文感知的推荐。
*   **地理信息系统 (GIS) 应用：** 利用 GIS 技术计算用户出发地与推荐城市之间的实际距离，并结合交通便利性作为推荐因子的重要组成部分，优化距离敏感型用户的推荐体验。

## 2.6 第三方 API 集成

为了丰富推荐维度并获取实时动态信息，本系统需要集成多个第三方 API。

**主要集成内容：**
*   **天气预报 API (QWeather)：** 通过集成和风天气（QWeather）API，获取指定城市未来 15 天的详细天气预报数据。这些数据将用于评估旅行期间的天气舒适度，例如避免恶劣天气、推荐气候宜人的城市，并作为推荐算法中的一个动态因子。对相同城市和日期的天气查询结果将进行缓存，以减少API请求次数和提升响应速度。
*   **地图与位置服务 API (高德/百度地图)：** 用于地理位置编码（将城市名称转换为经纬度）、逆地理编码、路线规划以及计算城市间的地理距离，支撑基于地理位置的推荐和筛选功能。
