# 第 3 章 系统分析

## 3.1 需求调研

为了确保旅游城市推荐系统能够精准满足用户需求并具备市场竞争力，本研究采取了多方面需求调研方法，包括在线问卷调查、用户访谈以及对现有旅游平台功能的分析。调研对象主要涵盖了具有不同旅游偏好、出行习惯的用户群体。

**核心需求提炼：**
通过对调研数据的归纳分析，我们提炼出用户对旅游城市推荐系统的三大核心需求： 1.
**个性化偏好匹配：**
用户希望系统能够根据其详细的兴趣标签（如自然风光、历史文化、主题乐园、美食文化、海滨休闲等）进行推荐。约
85% 的受访者表示，精准的兴趣匹配是其选择旅游目的地的首要考量因素。 2.
**动态信息感知：**
用户对推荐结果的时效性有较高要求，希望系统能结合实时或近实时信息进行推荐，如目的地天气、城市热度等。特别是在节假日期间，用户倾向于避开过度拥挤的热门城市或在恶劣天气时获取替代方案。
3. **便捷的交互体验：**
用户期待系统提供简洁直观的界面，方便快捷地输入偏好、筛选结果，并清晰展示推荐城市的详情，如评分、距离、推荐理由等。

**Kano 模型分析：** 基于Kano模型对用户需求进行优先级排序，发现： \*
**必备型需求：**
"根据兴趣标签推荐"和"天气情况提示"被归类为必备型需求，如果缺失将导致用户满意度大幅下降。
\* **期望型需求：**
"城市热度指数显示"、"距离优先筛选"和"行程时间优化"属于期望型需求，其实现将显著提升用户满意度。
\* **魅力型需求：**
"推荐理由详细解释"和"多维度综合评分"为魅力型需求，提供超出用户预期的价值。

**技术可行性评估：** 从技术角度，Spring Boot 后端服务能够支持高并发的
API 请求，MariaDB 和
Valkey（Redis）的组合可以满足数据存储和高速缓存的需求。Vue 3
框架能够构建丰富的交互式前端界面。整体技术栈已被验证具备构建本推荐系统的能力，预计系统能够支持日均
\[数十万\] 次的推荐请求。

## 3.2 功能性需求

本旅游城市推荐系统将提供以下主要功能：

### 3.2.1 用户管理模块

- **用户注册与登录：**
  提供用户注册、邮箱/手机验证、密码找回等功能，确保用户账户安全。
- **用户偏好设置：**
  允许用户自定义其旅游兴趣标签（多选）、设定出发城市、计划出行日期范围。用户可以随时修改个人偏好，系统将根据更新后的偏好重新生成推荐。

### 3.2.2 城市信息与标签管理

- **城市基础信息展示：**
  提供全国各城市的名称、省份、地理坐标等基础信息查询与展示。
- **城市特征标签管理：**
  系统内部维护一套精细化的城市特征标签体系（如自然风光、历史文化、美食文化等），并与各城市进行关联。该标签体系支持后台管理和动态更新。
- **城市热度数据：**
  整合来自第三方数据源（如用户点击量、搜索频率）的城市实时热度数据，用于推荐算法的动态因子。

### 3.2.3 核心推荐服务

- **个性化城市推荐：**
  根据用户的多维度偏好（兴趣标签、出发地、出行日期）以及动态环境信息（天气、城市热度），生成个性化的旅游城市推荐列表。
- **推荐结果筛选与排序：**
  用户可在推荐结果中进行二次筛选（如按距离、按评分、按天气等）和排序。
- **推荐理由展示：**
  为每个推荐城市提供详细的推荐理由，解释其如何匹配用户的偏好。

### 3.2.4 第三方数据集成

- **天气预报集成：**
  调用和风天气（QWeather）API，获取推荐城市的未来天气预报，并在推荐结果中展示。
- **地图与位置服务集成：** 调用地图
  API（如高德/百度地图），实现城市地理位置解析、距离计算，以及在前端地图上展示推荐城市位置。

## 3.3 非功能性需求

### 3.3.1 性能指标

- **推荐响应时间：** 在正常负载下（并发用户数
  \[100\]），核心推荐接口的平均响应时间应 ≤ \[500\] 毫秒。
- **数据加载速度：** 城市基础数据和用户偏好数据的加载时间应 ≤ \[200\]
  毫秒。
- **系统吞吐量：** 系统应支持至少 \[500\]
  次/秒的推荐请求，以应对旅游旺季的高并发访问。
- **缓存命中率：**
  常用数据（如城市详情、热门标签、天气预报缓存）的缓存命中率应 ≥
  \[85\]%。

### 3.3.2 可靠性与稳定性

- **数据一致性：** 用户偏好、城市信息等关键数据应保持强一致性。
- **系统可用性：** 系统应保证至少 \[99.5\]%
  的全年可用性，降低因服务中断造成的损失。
- **容错性：**
  数据库、缓存服务应具备主从备份、故障转移机制，确保单点故障不影响整体服务。第三方
  API 调用应具备重试和熔断机制。
- **数据备份与恢复：**
  定期进行数据库全量备份和增量备份，确保数据可恢复至任意时间点，RPO（恢复点目标）≤
  \[24\] 小时。

### 3.3.3 安全性要求

- **用户认证与授权：** 采用 Spring Security 结合 JWT（JSON Web
  Token）实现用户身份认证和基于角色的访问控制，确保只有合法用户才能访问受保护资源。
- **数据传输安全：** 所有前后端通信通过 HTTPS
  协议加密传输，防止数据窃听和篡改。
- **敏感信息保护：** 用户密码等敏感信息应进行加盐哈希存储。
- **输入校验：** 对所有用户输入进行严格的校验和过滤，防止 SQL 注入、XSS
  攻击等安全漏洞。
- **日志审计：** 记录关键业务操作和安全事件日志，便于审计和问题追溯。

## 3.4 可行性分析

### 3.4.1 技术可行性

- **技术栈成熟度：** Spring Boot、MariaDB、Valkey、Vue 3
  等主流技术栈均拥有广泛的社区支持、成熟的生态系统和丰富的开发资源。团队成员对这些技术栈具备一定的开发经验，降低了技术风险。
- **推荐算法可行性：**
  内容推荐、协同过滤及混合推荐算法理论成熟，已在多个领域得到广泛应用，并有大量开源实现可供参考和优化。地理信息系统（GIS）在计算距离、匹配位置方面也具备成熟的解决方案。
- **第三方 API 集成：** 和风天气、高德/百度地图等主流第三方 API
  提供了完善的开发文档和 SDK，集成难度适中。
- **数据处理能力：**
  结合MariaDB的关系型数据存储和Valkey的高速缓存，可以有效处理和管理推荐所需的用户偏好、城市特征及动态信息数据。

### 3.4.2 经济可行性

- **开发成本：**
  采用开源技术栈和轻量级框架，可以有效控制软件授权和开发工具成本。团队具备相关技术经验，可减少外部技术支持的依赖。
- **硬件投入：**
  系统采用前后端分离和微服务设计思想，可灵活部署在云服务器或物理服务器上。通过合理利用缓存和数据库优化，一台
  \[4核8G\] 的云服务器即可支撑系统初期运行，硬件投入成本较低。
- **潜在效益：**
  本系统有望通过提升用户满意度、增加用户黏性，间接为旅游企业和平台带来更高的商业价值。同时，精准的推荐能促进旅游资源的有效匹配和消费转化，带来可观的经济效益。预计投资回收周期为
  \[12-18\] 个月。

### 3.4.3 操作可行性

- **用户友好性：**
  前端界面将采用直观的设计和友好的交互流程，确保不同年龄段和技术水平的用户都能轻松操作。
- **管理与维护：**
  系统采用模块化设计，各组件职责明确，便于后续功能的迭代开发、升级和维护。日志系统和监控工具的集成，也使得系统运维更加便捷。
- **团队能力：** 团队成员具备 Java、Spring
  Boot、Vue.js、数据库、推荐算法等相关知识和开发经验，能够独立完成系统的设计、开发和部署。
