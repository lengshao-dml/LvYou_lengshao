# 第 6 章 系统测试

## 6.1 测试方案设计

为全面评估旅游城市推荐系统的功能性、性能和稳定性，本研究设计了一套综合性的测试方案。

**6.1.1 测试环境**
测试环境力求与生产环境保持一致，以确保测试结果的准确性。
*   **硬件配置：** 虚拟机环境，[4核8GB内存]，[100GB SSD] 存储。
*   **软件环境：** Spring Boot 后端服务、MariaDB 数据库、Valkey (Redis 兼容) 缓存，与生产部署的技术栈和版本保持一致。Vue 3 前端应用部署在独立的 Web 服务器上。
*   **网络环境：** 模拟真实用户网络环境，包括正常延迟和带宽限制。

**6.1.2 测试数据集**
测试数据来源于真实城市数据和模拟用户偏好数据。
*   **城市数据：** 包含 [全国 300+ 个] 城市的基础信息（名称、省份、经纬度）、[2000+] 条城市特征标签及关联数据。
*   **用户偏好数据：** 模拟 [1000] 个不同用户的兴趣标签、出发地和计划出行日期。
*   **天气数据：** 模拟第三方天气 API 返回的未来 [15] 天天气预报数据。
*   **城市热度数据：** 模拟 [300+] 个城市的实时热度分数。

**6.1.3 测试方法**
采用黑盒测试与性能测试相结合的方法。
*   **功能测试（黑盒测试）：** 基于系统功能性需求，设计测试用例，验证用户注册登录、偏好设置、个性化推荐生成、推荐结果筛选排序、城市详情展示、第三方数据集成等功能的正确性、完整性和可靠性。采用等价类划分、边界值分析等方法设计测试用例。
*   **性能测试：** 评估系统在高并发负载下的响应时间、吞吐量和稳定性。
    *   **压力测试：** 使用 JMeter 等工具模拟 [100] 到 [500] 个并发用户，对核心推荐 API 进行持续请求。
    *   **负载测试：** 模拟正常业务负载，长时间运行，观察系统各项指标变化。
*   **稳定性测试：** 持续运行系统 [24] 小时以上，监测内存使用、CPU 占用、接口错误率等，确保系统在长时间运行下无内存泄漏等问题。

## 6.2 功能测试结果

### 6.2.1 用户偏好管理测试

*   **测试场景：** 用户注册、登录、修改兴趣标签、修改出发城市、修改出行日期。
*   **测试结果：** 所有用户管理和偏好设置功能均按设计正常运行。用户成功注册登录，可灵活选择和修改兴趣标签，系统能够准确记录用户的出发地和计划出行日期。
*   **缺陷分析：** 暂未发现严重缺陷。

### 6.2.2 核心推荐服务功能测试

*   **测试场景：**
    *   基于单一兴趣标签推荐。
    *   基于多个兴趣标签组合推荐。
    *   考虑出发地距离的推荐。
    *   考虑天气因素的推荐（如晴天优先、避开雨雪）。
    *   考虑城市热度（如推荐热门城市或避开拥挤城市）。
    *   推荐结果的筛选和排序。
*   **测试结果：**
    *   **个性化推荐：** 系统能根据用户设置的兴趣标签、出发地、出行日期等条件，生成相应的旅游城市推荐列表。
    *   **动态因子融入：** 天气和城市热度因子在推荐算法中发挥作用，例如，在出行日期为雨天时，推荐结果中晴天城市的权重明显提升。
    *   **筛选排序：** 推荐结果可以根据距离、综合评分、天气舒适度等条件进行有效的筛选和排序。
*   **缺陷分析：** 在极端偏好组合下（如选择非常小众的兴趣标签且要求距离极近），推荐结果可能较少，但系统仍能返回最匹配的城市，而非空白结果。

### 6.2.3 第三方数据集成测试

*   **测试场景：** 和风天气 API 调用、地图 API (如高德/百度) 距离计算。
*   **测试结果：**
    *   **天气数据获取：** 成功从和风天气 API 获取指定城市的未来 15 天天气预报，并展示在前端界面。
    *   **距离计算：** 地图 API 返回的城市间距离计算准确，与实际地理数据误差在 [5]% 以内。
*   **缺陷分析：** 暂未发现严重缺陷。

## 6.3 性能测试分析

### 6.3.1 核心推荐 API 响应时间

使用 JMeter 模拟不同并发用户数对核心推荐 API (`/api/recommend`) 进行压力测试，结果如下：

**表 6-1 核心推荐 API 响应时间与吞吐量**

| 并发用户数 | 平均响应时间 (ms) | 90% 响应时间 (ms) | 吞吐量 (QPS) | 错误率 (%) |
| :-------- | :----------------- | :----------------- | :------------ | :--------- |
| 50        | [250]              | [320]              | [200]         | 0          |
| 100       | [400]              | [550]              | [350]         | 0          |
| 200       | [800]              | [1200]             | [450]         | [2]        |
| 300       | [1500]             | [2500]             | [480]         | [5]        |

*   **分析：** 在 [100] 并发用户以内，系统表现良好，平均响应时间控制在 [500] 毫秒以内，吞吐量较高。当并发用户数达到 [200] 时，响应时间显著增加，并开始出现少量错误，表明系统性能达到拐点。

### 6.3.2 缓存效果评估

*   **测试场景：** 针对天气预报查询、热门城市列表查询进行带缓存和不带缓存的性能对比。
*   **测试结果：**
    *   **天气查询：** 启用 Valkey 缓存后，天气 API 查询的平均响应时间从 [200] ms 降低到 [5] ms，提升效果显著。
    *   **热门城市列表：** 缓存命中率达到 [90]% 以上，数据库查询压力明显降低。

### 6.3.3 资源占用分析

*   **CPU 占用：** 在 [100] 并发下，后端服务 CPU 占用率稳定在 [60-70]%。MariaDB 和 Valkey 的 CPU 占用率相对较低。
*   **内存使用：** 后端服务内存使用量稳定在 [500] MB 左右，无明显内存泄漏。Valkey 缓存占用内存约 [100] MB。

## 6.4 测试结论与待改进问题

### 6.4.1 测试结论

本旅游城市推荐系统经过全面的功能和性能测试，已达到设计目标中的大部分指标：
1.  **功能性：** 核心功能（用户偏好管理、个性化推荐、第三方数据集成）实现完整，满足用户个性化旅游推荐的需求。
2.  **性能：** 在中低并发负载下，系统响应速度和吞吐量表现良好，能够支持 [日均数十万次] 的推荐请求。
3.  **稳定性：** 系统连续运行 [24] 小时无宕机，资源占用稳定，初步验证了系统的可靠性。

### 6.4.2 待改进问题

1.  **高并发下的性能瓶颈：** 在 [200] 以上的并发用户场景下，系统响应时间显著增加，存在性能瓶颈。初步分析可能与推荐算法的计算复杂度或数据库查询优化仍有空间有关。未来可考虑引入更高效的推荐算法、对数据库进行读写分离或分库分表。
2.  **推荐算法的精确度提升：** 虽然当前推荐准确率达到 [85]%，但在某些复杂偏好组合或新用户冷启动场景下，推荐结果仍有优化空间。未来可引入深度学习模型、用户隐式反馈（如点击、停留时间）进一步优化推荐算法。
3.  **实时性优化：** 尽管天气数据已缓存，但城市热度等动态信息的更新频率和实时性仍可进一步提升。考虑引入消息队列与流处理技术（如 Kafka + Flink），实现更实时的动态信息处理和推荐更新。
4.  **用户反馈机制完善：** 目前系统主要基于用户显式偏好。未来可加入用户对推荐结果的反馈机制（如“喜欢”、“不喜欢”），形成闭环，持续优化推荐模型。
