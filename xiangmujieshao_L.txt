旅游城市推荐系统项目介绍

  项目概述与目标：
  本旅游城市推荐系统旨在解决当前旅游市场信息过载和传统推荐系统个性化不足的问题。它致力于根据用户的多维度偏好（兴趣、地理位置、出行时间）以及结合天气、城市热度等动态信息，为
  用户智能生成个性化的旅游城市推荐列表，从而提升用户的旅游决策效率和满意度。

  1. 主要功能：
  该系统提供以下核心功能：

   * 用户管理： 支持用户注册、登录，以及个人账户信息管理。
   * 用户偏好设置： 允许用户自定义其旅游兴趣标签（多选，如自然风光、历史文化、美食文化等）、设定出发城市和计划出行日期范围。
   * 城市信息与标签管理： 提供全国各城市的名称、省份、地理坐标等基础信息查询，并维护一套精细化的城市特征标签体系。
   * 个性化城市推荐： 根据用户的多维度偏好和动态环境信息（天气、城市热度），生成高度个性化的旅游城市推荐列表。
   * 推荐结果筛选与排序： 用户可以在推荐结果中进行二次筛选（如按距离、按评分、按天气）和排序。
   * 推荐理由展示： 为每个推荐城市提供详细的推荐理由，解释其如何匹配用户的偏好。
   * 第三方数据集成： 集成和风天气 API 获取实时天气预报，以及地图 API（如高德/百度地图）进行地理位置解析和距离计算。
   * 系统界面演示： 提供用户偏好输入界面、推荐结果展示界面和城市详情页面，具备直观友好的交互体验。

  2. 具体工作流程：
  系统的工作流程可以概括为以下步骤：

   1. 用户偏好收集： 用户通过前端界面输入或修改其出发城市、旅游兴趣标签和计划出行日期。
   2. 数据获取： 后端服务接收用户请求，并从数据库（MariaDB）中获取用户的偏好、城市的基础信息和特征标签。同时，系统会调用第三方天气 API
      获取指定城市在特定日期的天气预报，并获取城市热度数据（部分数据会从 Valkey 缓存中获取以提升效率）。
   3. 推荐算法执行：
       * 偏好匹配度计算： 系统计算用户兴趣标签与各个候选城市特征标签的匹配程度。
       * 地理距离计算： 计算用户出发地与候选城市之间的距离。
       * 天气舒适度评估： 根据天气预报数据，评估各城市在用户出行期间的天气舒适度。
       * 城市热度因子获取： 获取各候选城市的当前热度分数。
       * 多因子加权融合： 将上述所有因子（偏好匹配度、地理距离、天气舒适度、城市热度）进行加权求和，为每个候选城市生成一个综合评分。
   4. 结果排序与展示： 系统根据综合评分将所有候选城市降序排列，并筛选出 Top N 个城市。这些推荐城市连同其推荐理由、天气概览、距离等信息，通过 RESTful API 返回给前端。
   5. 用户交互与反馈： 前端界面将推荐结果列表展示给用户，用户可以进一步筛选、排序或查看城市详情。

  3. 主要模块：
  系统采用四层分布式架构，主要模块包括：

   * 展示层 (前端)： 基于 Vue 3 构建，负责用户界面、交互和推荐结果展示。
   * 业务逻辑层 (后端)： 采用 Spring Boot 框架，提供 RESTful API，处理用户请求、协调服务层、执行业务逻辑（如用户认证、数据聚合）。
       * 推荐控制器 (RecommendationController)
       * 用户控制器 (UserController)
       * 城市控制器 (CityController)
       * 天气服务 (WeatherService)
   * 服务层：
       * 推荐算法模块： 封装核心推荐算法逻辑。
       * 用户偏好模块： 管理用户兴趣标签和偏好。
       * 城市数据模块： 提供城市基础信息和特征。
       * 第三方天气API集成： 调用和风天气等外部服务。
       * 第三方地图API集成： 调用高德/百度地图等外部服务。
   * 数据层：
       * MariaDB 数据库： 用于持久化存储用户、城市、标签、天气预报历史、城市热度等结构化数据。
       * Valkey (Redis 兼容) 缓存： 用于高速缓存热门数据、API 响应结果等，提升系统响应速度。

  4. 数据结构（主要数据库表）：
  系统在 MariaDB 中设计了以下主要表结构：

   * user 表： 存储用户ID、用户名、密码哈希、邮箱、创建/更新时间、当前城市等。
   * city 表： 存储城市ID、名称、省份、经纬度、描述、创建/更新时间等。
   * tag 表： 存储兴趣标签ID、名称、类型（如“自然风光”），以及创建/更新时间。
   * user_interest_tag 表： 关联用户与兴趣标签，记录用户的兴趣偏好。
   * city_feature_tag 表： 关联城市与特征标签，记录城市的旅游特色及其权重。
   * weather_forecast 表： 缓存天气预报数据，包括城市ID、预报日期、天气状况、温度范围、更新时间等。
   * city_popularity 表： 存储城市热度分数，包括城市ID、热度分数、更新时间。

  5. 用户画像构建：
  用户画像的构建是系统实现个性化推荐的基础，主要通过以下方式：

   * 显式偏好收集： 用户在注册或个人设置中主动选择的旅游兴趣标签、设定的出发城市和计划出行日期，这些是用户画像的核心静态数据。
   * 地理位置信息： 用户的出发地（或当前位置）被视为一个重要偏好，用于计算距离因子。
   * 动态偏好捕捉（未来拓展）：
     虽然目前系统主要依赖显式偏好，但未来的用户画像可以进一步通过分析用户的搜索历史、点击行为、停留时间等隐式反馈来丰富，以捕捉用户动态变化的兴趣。

  6. 算法实现：
  推荐算法是系统的核心，采用多因子加权融合的策略，为每个城市计算综合评分：

   * 评分因子：
       * 用户偏好匹配度 (PreferenceScore)： 计算用户兴趣标签集合与城市特征标签集合的 Jaccard 相似度。
       * 地理距离因子 (DistanceScore)： 使用 Haversine 公式计算用户出发地与候选城市之间的距离，距离越近得分越高。
       * 天气舒适度因子 (WeatherScore)： 根据未来天气预报评估城市天气对旅行的适宜程度，适宜天气得分高。
       * 城市热度因子 (PopularityScore)： 归一化城市的热度分数，体现城市的受欢迎程度。
   * 综合评分公式：
      FinalScore = w_pref * PreferenceScore + w_dist * DistanceScore + w_weather * WeatherScore + w_pop * PopularityScore
      其中 w_pref, w_dist, w_weather, w_pop 是各因子的权重，且总和为 1。这些权重可以根据实际效果或业务需求进行调整。
   * 实现技术： 推荐逻辑在 Spring Boot 后端服务中实现，利用 MariaDB 查询城市和用户数据，并结合 Valkey
     缓存获取天气和热度等实时性要求较高的数据。距离计算通过独立的工具类实现。

  这个项目致力于提供一个功能全面、性能良好且具有高度个性化能力的旅游城市推荐解决方案，以满足现代旅游者不断增长的定制化需求。
  一、 项目核心工作流程

整个系统的工作流程可以分为四个主要部分：

1. 用户画像构建 (双重画像)

注册画像 (静态)：用户注册时，会提供常居城市和一组兴趣标签（如“历史文化”、“美食文化”），并可以为这些标签赋予初始的权重。这构成了用户的初始画像基础。

行为画像 (动态)：在用户使用过程中，系统会默默记录其关键行为：

搜索行为：记录用户搜索的关键词。

点击行为：记录用户在推荐列表中点击了哪个城市。

隐式反馈：这是最智能的部分。当用户点击某个城市后，系统会分析该城市的特色标签，并自动、少量地增加用户画像中对应标签的权重。例如，用户频繁点击“自然风光”的城市，系
统就会判断他对此类景点更感兴趣，后续会为他更多推荐此类城市。




2. 热门城市计算

这是一个独立于用户个性的全局推荐模型。系统会根据所有用户的搜索次数和点击次数来计算每个城市的“热度分”。

我们设定了一个公式 score = search_count * 0.3 + click_count * 0.5。

一个后台定时任务会每小时自动运行，更新所有城市的热度排名。这确保了“热门推荐”是实时、由真实用户行为驱动的。



3. 个性化推荐生成

当用户请求推荐时，后端会执行一套复杂的评分算法。

获取用户画像：如果是登录用户且没有在请求中临时指定兴趣，系统会从数据库中加载他最新的、经过动态调整的个人兴趣权重图谱。

向量空间模型：系统会将用户的兴趣画像（一个带权重的标签列表）和每个候选城市的特征画像（拥有的景点标签）都转换为高维向量。

余弦相似度算法：通过计算用户兴趣向量和每个城市特征向量之间的“夹角”（余弦相似度），来判断该城市与用户的兴趣匹配度有多高，得出一个标签得分。

综合评分：最终得分由三部分加权构成：

1. 标签匹配分 (60%)：上一步计算出的余弦相似度得分。


2. 距离分 (20%)：根据用户选择的距离范围（如“500km内”、“省内”等），离出发地越近，得分越高。


3. 天气分 (20%)：调用天气服务接口，获取目标城市在计划日期的天气。“晴天”得分最高，“大雨”则会拉低分数。



返回结果：系统将所有候选城市按综合评分排序，返回前 10 名作为最终推荐结果。



4. 前端展示与交互

用户在首页的表单中输入出发城市、出行日期和（可选的）临时兴趣标签。

后端返回推荐结果后，前端以卡片形式展示城市列表，包括分数、距离、天气等信息。

首页还开辟了“热门推荐”模块，直接调用热门城市接口，为用户提供一个发现新去处的快速通道。

当用户点击任何一个城市卡片时，前端会将点击事件发送回后端，从而触发我们前面提到的“动态用户画像更新”流程，形成一个完整的学习和推荐的闭环。

二、 核心数据结构

为了支撑上述流程，我们定义了以下关键的数据模型：

用户 (User): 存储用户名、密码、邮箱等基础信息，以及关联的 homeCityId (常居城市ID)。

城市 (City): 包含城市名称、省份、经纬度等静态信息。

标签 (Tag): 兴趣标签表，如“历史文化”、“自然风光”等。

城市特征 (CityFeature): 关联 City 和 Tag，表明一个城市拥有哪些类型的景点。

用户兴趣标签 (UserInterestTag): (静态与动态画像核心)

这是用户画像的关键表，关联了 User 和 Tag。

核心字段是 weight (权重)，它在用户注册时被初始化，并在用户产生点击行为后被动态调整。


城市热度 (CityPopularity): (热门推荐核心)

关联 City。

包含 search_count (搜索计数) 和 click_count (点击计数) 两个字段，由用户行为实时更新。

score (热度分) 字段由后台定时任务根据前两个计数值计算并更新。


行为日志表:

UserSearchHistory (用户搜索历史)

UserClickHistory (用户点击历史)

UserRecommendLog (用户推荐请求记录)

这些表记录了用户的详细行为，是后续进行更复杂数据分析和模型优化的基础。
